## Commands

- `flutter pub get` — install dependencies
- `flutter run` — run on a connected device/emulator
- `flutter analyze` — static analysis (uses `package:flutter_lints/flutter.yaml`, no custom rules in `analysis_options.yaml`)
- `flutter test` — the only test file, `test/widget_test.dart`, is unmodified stock boilerplate that references a nonexistent `MyApp` widget (the real root widget is `BrikStaxApp` in `lib/main.dart`); it fails as-is and is not a signal of anything. There is no real test suite in this repo.
- `flutter build apk` / `flutter build appbundle` / `flutter build ios` — release builds. The Flutter SDK on this machine lives outside PATH at `/c/flutter/flutter/bin/flutter.bat` — use the full path from a bash shell rather than assuming `flutter` resolves. Play Store submissions want the App Bundle (`build\app\outputs\bundle\release\app-release.aab`), not the APK.
- **Known environment limitation**: Gradle builds (`flutter build apk`/`appbundle`) fail with `java.io.IOException: Unable to establish loopback connection` when run from this Bash tool's shell — a sandbox/process networking restriction, not a project bug (confirmed: fails identically with `--no-daemon`, with the sandbox disabled, and with `-Djava.net.preferIPv4Stack=true`). `flutter analyze`/`flutter pub get`/`flutter test` all work fine from here; only the actual Gradle build step needs to be run by the user in their own PowerShell/terminal session. If a build fails there with `Unsupported class file major version 70` instead, that's a JDK mismatch — the machine has both JDK 21 (Android Studio's bundled `C:\androidstudio\jbr`, correct) and a newer system JDK on `JAVA_HOME`/PATH; fix with `flutter config --jdk-dir="C:\androidstudio\jbr"`. **Build-verified 2026-08-13** — user confirmed the app builds and runs well on-device with the current `android/build.gradle.kts` overrides (see that section below); trust that fix now, it's no longer just "confirmed by reading the dependency's own build.gradle."

## Architecture

### Startup and state wiring (`lib/main.dart`)

`main()` is wrapped end-to-end in `SentryFlutter.init(..., appRunner: () async { ... })` — not just around `runApp`, but around the entire singleton-init sequence too, so a crash during startup (not just at runtime) is still captured. `_kSentryDsn` holds the DSN; a DSN is a write-only client identifier, not a secret, safe to commit (same trust level as the Rebrickable/BrickSet keys already embedded elsewhere) — left blank, the SDK silently no-ops instead of erroring, so it's safe to ship either way.

A long list of avatar-module singletons are explicitly `.init()`'d in sequence before `runApp` (`AchievementService`, `LootService`, `DevMode`, `DailyFiveService`, `HiddenThemeService`, `WishlistService`, `ThemeService`, `FeatureFlagService`, `DeviceIdentity`). Only three of these end up in the `MultiProvider` (`CollectionProvider`, `WishlistService`, `CommunityService`) — the rest are plain `ChangeNotifier` singletons (`Xyz.instance`) consumed directly via `ListenableBuilder` or by calling methods on the singleton, not via `context.watch`/`Provider.of`. `ThemeService` in particular drives `MaterialApp.theme` through a top-level `ListenableBuilder`, bypassing Provider entirely. When wiring new global state, match whichever pattern the thing you're touching already uses rather than assuming Provider is universal.

`kWishlistEnabled` / `kCommunityEnabled` in `main.dart` are the single source of truth for whether those tabs/screens exist at all (nav items, `IndexedStack` children, and FAB visibility all key off them) — toggle features by flipping these, not by hiding widgets downstream.

### Anonymous device identity (`services/device_identity.dart`)

Generates a random UUID once per install (via the `uuid` package, already a dependency), persists it in SharedPreferences, initialized in `main.dart` alongside the other singletons. This exists specifically because two backend features are keyed by a per-device identifier: barcode-submission consensus voting (`/barcode/submit` on the Worker counts `COUNT(DISTINCT user_id)` per barcode, with a `UNIQUE(barcode, user_id)` constraint) and Community submission cooldowns (rate-limited per `user_id`). Before this existed, every install sent the literal string `'local_device_user'` — meaning the barcode consensus threshold could never be reached with more than one real tester (they all collapsed into one row), and one tester posting to Community locked out every other tester for the cooldown window. Both `community_feed_screen.dart` and `scanner.dart` call `DeviceIdentity.instance.id` for this; `init()` must run before either is used, which is why it's in the `main.dart` startup sequence.

### Pixel-art avatar system (`data/pixel_cosmetics.dart`, `widgets/pixel_avatar_widget.dart`) — replaced the sprite figure catalog

The figure (head/hat/torso/legs/item) is a from-scratch pixel-art system now, not the old detailed-photo-crop catalog. `PixelCosmetic`/`PixelSlot` is its own catalog under `assets/avatar_pixel/`, deliberately **not** merged into `data/background_cosmetics.dart`, which is now **backgrounds-only** (the old ~130-entry helmet/head/outfit/accessory catalog was deleted outright, not migrated). `AvatarState` was cut over to match: `helmetId`/`outfitId`/`accessoryId` are gone, replaced by `hatId`/`torsoId`/`legsId`/`itemId` pointing at `PixelCosmetic` ids; `backgroundId` is untouched and still resolves through `background_cosmetics.dart`/`backgrounds_art.dart` exactly as before. Old saves reset to `AvatarState.defaults` automatically on this cutover — the old JSON field names don't match the new ones, so `fromJson` just doesn't find them and falls back to defaults, no migration code needed (a deliberate choice, not an oversight, since there was no real user base yet to protect).

**Grew well past its original 20-item starting size** (2 heads, 5 hats, 5 torsos, 4 legs, 4 items) to ~103 real entries with rarity tiers, descriptions, and per-item compositing tuning (`offsetX`/`offsetY`/`scale`) — including a 4-slot animated "Chrome" legendary set (hat/torso/legs/item, 4-frame shine sweep each) and one `isSecret` item (`px_item_secretxwing`, 8-frame animation). This happened outside any session Claude was present for (no corresponding commit history at the time of writing), so treat the exact count/roster as worth re-checking in `pixel_cosmetics.dart` directly rather than trusting this number to stay current. Every achievement/hidden-theme/bundle `cosmeticId`/`rewardCosmetic` reference was re-pointed at real ids in this expanded catalog as part of the same change — checked exhaustively 2026-08-12, all resolve. `LootService._rewardPool`/`_maybeSecretDrop` also draw from both `allBackgroundCosmetics` and `pixel.allPixelCosmetics` now, not backgrounds-only — see Reward pool section below. Two equip paths on `AchievementService`: `equipPixel()` for the figure catalog, `equipBackground()` for background only (a simple `if (slot == background) return` now, not a switch over dead cases — see next paragraph). `bundle_popup.dart`/`loot_roll_widget.dart`/`loot_service.dart`'s `equipBundle` all followed the same simplification independently.

**2026-08-12: `sprite_cosmetics.dart` renamed to `background_cosmetics.dart`**, along with every type it declares (`SpriteCosmetic` → `BackgroundCosmetic`, `SpriteRarity`/`SpriteRarityX` → `CosmeticRarity`/`CosmeticRarityX` — renamed generic rather than `Background*` since it's the shared rarity scale both catalogs use, `PixelRarityX.asSpriteRarity` → `.asCosmeticRarity`, `allSpriteCosmetics`/`spriteCosmeticsById` → `allBackgroundCosmetics`/`backgroundCosmeticsById`, import alias `sprite` → `bg` everywhere it was aliased). The old name was a real source of confusion, not just aesthetic — it read as legacy/dead leftover code from the retired figure catalog, when this file was actually its entire live purpose (52 real backgrounds). `spriteCosmeticsForSlot()` was deleted outright rather than renamed — with `CosmeticSlot` down to one value, a filter-by-slot function was itself misleading about there being something to filter; its one call site (`avatar_editor.dart`) now just reads `allBackgroundCosmetics` directly. Same pass also removed the last leftovers from the deleted figure catalog now confirmed unreferenced — `CosmeticSlot`'s `helmet`/`head`/`outfit`/`accessory` values (down to just `background`), the now-pointless `AccessoryPlacement`/`HeadCoverage` enums and `BackgroundCosmetic.placement`/`coverage`/`outfitWidthScale`/`frames` fields (none used by any of the 52 background-only catalog entries), and one real dead switch case (`achievement_popup.dart`'s `_bgSlotEmoji`, formerly `_spriteSlotEmoji`, the only place still switching over all the old `CosmeticSlot` values instead of a simple background check like everywhere else). `loot_service.dart`'s `_starterIds` also had three stale ids (`head_01`/`helmet_38`/`outfit_34`) trimmed back to just `bg_cream`, the only one still doing real work.

`AvatarStorage._sanitize()` validates against `pixelCosmeticsById` now, not `backgroundCosmeticsById`. Same head/torso/legs-must-never-be-blank vs. hat/item-can-be-null split as the old system had for head/outfit vs. accessory.

`AvatarWidget` (`widgets/avatar_widget.dart`) is the shared adapter every screen actually renders through (dashboard card, achievement/bundle popups, loot roll reveal, Den scene) — it wraps `PixelAvatarWidget` internally and still does the background-badge compositing itself, so swapping the figure renderer only required changing this one file, not each call site. `animated` and `showGroundAccessory` are accepted params that currently do nothing: the pixel catalog has no per-frame animation yet, and `itemId` (trophy/brick stack/watering can/toolbox) exists in the data model and is equippable in the editor but isn't rendered anywhere yet, on-figure or as a ground accessory — `ground_accessory.dart`'s `groundAccessoryOf()` always returns `null` for this exact reason (the old `AccessoryPlacement` semantics it read don't exist on `PixelCosmetic`), so both Den-scene call sites correctly render nothing rather than crash.

`avatar_editor.dart` was rebuilt for the new catalog: tabs are Head/Hat/Torso/Legs/Item/Den now (was Helmet/Outfit/Item/Den). `_pixelGrid`/`_PixelTile` originally shipped simpler than the background grid (flat, no rarity, everything unlocked, per this doc's older text) but was brought up to parity at some point outside any session Claude was present for (no corresponding commit history) — it now mirrors `_bgGrid`'s shape exactly: Unlocked/Locked groups subdivided by rarity tier, gated by `AvatarState.starterIds` + `unlockedIds` the same way backgrounds always were, plus an ungated "None" tile on the two optional slots (Hat, Item) to clear them. Background keeps its own separate grid/tile (`_bgGrid`/`_BgTile`) since it's on a different underlying catalog, but the two are no longer different in maturity — same unlocked/locked/rarity treatment on both now.

### Pixel avatar compositing (`widgets/pixel_avatar_widget.dart`) — anchor points, not per-item scale correction

Fixed 64-wide art-pixel body canvas, split vertically into head/torso/legs zones, plus a hat overflow band above it anchored to a single crown pixel — same "anchor pixel, not bounding-box fit" principle the original ground-up spec called for, and so far it's held up without needing a per-item correction factor the way the old outfit system did (see git history for the old catalog's `outfitWidthScale` field, deleted 2026-08-12 as dead code, if that era's approach is ever relevant again).

The vertical split (currently head 28 / torso 32 / legs 36, out of 96) and every zone's width went through three tuning passes against real on-device screenshots, not a formula:
1. Original spec (40/32/24, a 5:4:3 ratio) assumed each zone's raw canvas aspect ratio told you the actual character content's shape — it didn't. The real generated art has a lot of transparent margin baked in around the content (e.g. the head canvas is 1:1, but the actual head silhouette inside it is ~0.78:1, portrait not square). Fixed by auto-cropping all 20 assets to their real opaque bounding box (a one-off PowerShell script using `System.Drawing`/`LockBits`, not checked into the repo) and recomputing zone widths from the cropped content's average aspect ratio per category.
2. Second pass (38/26/32) fixed legs reading as stubby doll-legs at 24 units (25% of body height), but overcorrected the head/hat, which still read as visually dominant.
3. Current pass (28/32/36) trims head further, grows torso and legs — direct feedback against a render, no principled formula behind the specific numbers. If head/hat ever look under-sized, that's the signal to nudge back the other way.

Head/torso/legs use `BoxFit.fill`, not `contain` — with zone aspect now matching cropped-content aspect closely, `fill` guarantees both seam edges (neck, waist) touch exactly with no gap, trading a barely-visible stretch on outlier items for never breaking the connected-figure illusion. Hat is the one exception, staying on `BoxFit.contain` + `Alignment.bottomCenter` with a deliberate `_hatDip` (7 units) overlap into the head zone rather than a flush anchor: hats drawn at an angle (a brim projecting down and to the side) have their bounding-box bottom at the brim *tip*, not at the part of the hat that actually sits near the hairline, so anchoring flush to that bounding box read as a gap above the head. Z-order is legs → torso → head → hat, same rule and same reason as the old sprite system (torso over the leg waistband, head over the torso collar, hat covers hair last).

### Secret cosmetics (`services/secret_item_service.dart`, `services/loot_service.dart`)

`isSecret` marks an item as a hidden surprise, on either catalog now (`PixelCosmetic` in `pixel_cosmetics.dart` — currently one real entry, `px_item_secretxwing`, an 8-frame-animated X-Wing Fighter — or `BackgroundCosmetic` in `background_cosmetics.dart`, though no background currently sets it). `SecretItemCodes.byCode` maps a magic code to a cosmetic id the same way `DevMode.magicId` works, checked in `CollectionProvider.addSet` right after the `DevMode` check.

**Fixed 2026-08-12, was dead in practice before**: `byCode`'s only entry (`'110555' -> 'accessory_57'`, a Flux Capacitor Case) pointed at an id from the head/helmet/outfit/accessory catalog deleted in the pixel-art cutover — `handleCode()` was silently returning null for it. Removed rather than repointed, since no secret item has been designated code-unlockable yet; add a fresh `{code: id}` entry once one is (pixel or background id, both work now — `handleCode()`/`_grant()` were also fixed to check `pixelCosmeticsById` as well as `backgroundCosmeticsById`, since they only ever checked the background side before, which would have hit this exact same silent-failure mode again for a code pointed at a pixel id). The X-Wing itself is reachable today only through `LootService._maybeSecretDrop()`'s rare bonus-roll path, not by code — nothing currently in `byCode` grants it.

### Reward pool exclusivity and dupe compensation (`services/loot_service.dart`, `services/hidden_theme_service.dart`)

`LootService.unlockOrDupePayout(id, unlockedIds)` is the one shared helper behind every grant path that can hand out an id the player might already own — `claimDaily`, `grantBonusRoll`, `equipBundle`, `unlockBundle` here, and `HiddenThemeService.checkAndGrant()` — replacing what used to be the same "already owned? pay Briks : unlock" branch copy-pasted five times. `_rewardPool` and `_maybeSecretDrop` both draw from `allBackgroundCosmetics` (backgrounds) and `pixel.allPixelCosmetics` (figure) together, excluding `isSecret` items and anything referenced as a hidden-theme tier reward or bundle piece (`_themeAndBundleIds`) from either catalog — see the pixel-art section above for when this stopped being background-only.

### Daily 5 (`services/daily_five_service.dart`, `widgets/daily_five_screen.dart`)

`DailyTask` is a 5-value enum whose completion state persists as a `Set<int>` of `.index` values (`_done`, see `_save`/`init`). Swapping what a slot *does* (e.g. `polish` → `portfolio`, when trophy polish was cut as a feature) means renaming the enum value **in its existing position**, not reordering or replacing it — the index is the only thing actually persisted, so a rename-in-place keeps anyone's already-completed "done" state for today decoding correctly, while removing/reordering values would silently corrupt it.

A local (on-device) reminder notification for unfinished Daily Five tasks (`services/local_notification_service.dart`, `flutter_local_notifications`/`timezone`/`flutter_timezone` packages) was added 2026-08-09 — distinct from `push_service.dart`'s FCM stack, see that file's own doc comment for the local-vs-server-push architecture split. Rolls once per day (60% show probability, random time in a 4pm-8pm window, both persisted so repeat sync calls don't re-roll) and pays a +10 Brik top-up on `claimBonus()` specifically on days the reminder actually fired (`DailyFiveService.markReminderNeeded()`/`_reminderNeeded`, a real DB column added via a `version: 2` migration). `flutter_local_notifications` pulled in a real, standard Android build requirement, not a project-specific workaround: `android/app/build.gradle.kts` needed `isCoreLibraryDesugaringEnabled = true` + the `desugar_jdk_libs` dependency, since the plugin's AAR metadata declares a dependency on Java 8+ APIs (`java.time`, etc.) not natively available below API 26.

**Real bug fixed 2026-08-15**: `syncDailyFiveReminder()` called `markReminderNeeded()` (which makes the +10 Brik bonus claimable) *before* checking whether today's randomly-rolled reminder time had already passed — contradicting its own doc comment ("needed AND will actually show today"). A late app-open, after the rolled window had already elapsed, could grant the bonus for a nudge that was never actually shown. Fixed by reordering: the `today.isBefore(now)` bail-out (no notification will fire) now runs first, before `markReminderNeeded()`.

**`LootService.streak.canClaim` staleness fixed 2026-08-15**: `canClaim` was only ever recomputed against the current date at cold app start (`DailyStreak.fromJson`, called exclusively from `LootService.init()`) — there's no `AppLifecycleState` observer anywhere in this app, so a session that stayed alive across local midnight (backgrounded, not force-quit) kept showing yesterday's "already claimed" state until a full restart. Affects all 4 real read sites at once, since they all just read `.streak.canClaim` directly: the Daily Brick claim screen, the dashboard claim card, `DailyFiveService.isDone(checkin)` (reads this same flag), and `claimDaily()`'s own guard. Fixed at the one shared source instead of each call site — the `streak` getter itself now self-corrects (recomputes and flips `canClaim` true if a new day has started) rather than requiring every caller to know to check first.

### Backgrounds / "Brick Den" — image art wired in, 4 ids still procedural-only

`bgArt.bgPalettes` (`data/backgrounds_art.dart`) is a `Map<String, BgPalette>` keyed by `bg_*` id and is the single source of truth for both the avatar's circular backdrop color *and* the Den scene's wall/floor colors when no image exists for that id. `bgArt.bgImageIds` (a `Set<String>`) and `bgArt.denImageAsset(bgId)` are the actual source of truth for whether a `bg_*` id has real generated art at `assets/avatar/dens/<id>.png` — 48 of the 52 catalog ids do; `bg_workbench`, `bg_snowfield`, `bg_maproom`, and `bg_shadowrealm` don't (no image was ever generated for them) and keep falling back to the procedural painter.

`widgets/brick_den.dart` is screen chrome only (header, back/share buttons) — the actual scene, showcase, and trophy content lives in `widgets/den_scene.dart`'s `DenSceneContent`, which `BrickDenScreen` just embeds. This split exists so the Avatar Editor's Den tab (`avatar_editor.dart`, labeled "🏠 Den" — it replaced the old flat background-swatch grid) can embed the exact same live scene without nesting a second full `Scaffold` inside a `TabBarView`. Background-picking didn't disappear with the grid — it moved into a `showModalBottomSheet`/`DraggableScrollableSheet` reached via a "Change Background" button floating over the scene, still built from the same `_bgGrid` used there before.

Both `den_scene.dart`'s private `_DenPainter` and `widgets/den_share_screen.dart`'s self-contained public `DenPainter` (kept in sync by hand — the latter's doc comment states it intentionally does not depend on `den_scene.dart`/`brick_den.dart` internals) check `bgArt.denImageAsset(bgId) != null` (`hasImage`) and, when true, skip painting the wall/floor/window/per-theme wall decor entirely — an `Image.asset` painted just behind the `CustomPaint` supplies all of that instead. What the painter still always draws on top, image or not, is the dynamic HUD: badges, the trophy shelf, and the diamond trophy. When `hasImage`, each of those additionally skips its own "locked/empty" placeholder (a flat gray plaque that read fine against a painted wall but looks like a rendering glitch against a photo) — only actually-earned content draws once real art is present. The top-3 showcase boxes are the one exception to "earned content still draws" — see below.

The top-3 showcase boxes (the colored value indicators, not just their pedestal) are skipped entirely once `hasImage` — this went through two rounds of revision. First the floor-toned pedestal alone was cut (same reasoning as the rug/badge/trophy placeholders: tuned to blend into the procedural floor, reads as a disconnected gray box against a photo), keeping the colored block itself since it was real earned content. Then the block's own "highlight frame" accent spark was cut too (`brick_den.dart`/`den_scene.dart` only, `den_share_screen.dart` never had it) since it cycled across the three blocks in sequence as the animation frame advanced, reading as one light sweeping across all three rather than three independent highlights, and each block+cap on its own already looked like a candle with a floating flame above it once the pedestal was gone. Feedback kept landing back on the boxes themselves even after both of those fixes, so the whole loop is now skipped outright once `hasImage` (`for (int i = 0; i < 3 && !hasImage; i++)`) — they read as flat procedural cubes against real photo art no matter what's done to their base or highlight, and they're redundant anyway: the text label bar below the scene (name + price per top-3 set) already shows the same information.

The avatar's own square bounding box (`avatarSize`, currently `pxd*36` in both files) is intentionally much bigger than the visible character (`SpriteAvatarWidget`'s figure only fills part of its own box — see above), and is grounded via `top: pxd*<groundRow> - avatarSize*.99` where `.99` is the outfit region's `top+height` fraction — `<groundRow>` is tuned per feedback (currently 43, i.e. feet planted well past the wall/floor seam at row 36) and is the thing to adjust if the figure ever needs to move up/down in the scene without changing its size.

A ground-placement accessory (`AccessoryPlacement.ground`) is **not** rendered through `AvatarWidget`/`SpriteAvatarWidget` in the Den or its share card — both pass `showGroundAccessory: false` and instead render the equipped ground accessory as its own `Positioned` `Image.asset`, looked up via `_groundAccessoryOf(state)` (duplicated in both files) and placed at a fixed scene-relative spot (currently `pxd*30, pxd*30`, sized `pxd*19.5 x pxd*16.5`) tuned to sit on the floor in the gap between the figure and the shelf/table, not up on the shelf itself. This is deliberate: `SpriteAvatarWidget`'s own `_accessoryRegions` are fractions of *the avatar's own box*, which has no relationship to where the shelf sits in the photo — "beside the figure" (what the shared region system gives you, still used by the Minifig editor and the small `showBackground: true` badges/popups) and "on the floor in front of the shelf" (what the Den needs) are two different reference frames that can't be satisfied by one shared value. Since this layer bypasses `SpriteAvatarWidget`, it also doesn't get that widget's per-frame animation for free: `den_scene.dart`'s `_DenSceneContentState` computes its own `_accFrame` in `_onTick`, off the *same* `AnimationController` that drives the badge/trophy shimmer (`_frame`) — but that controller runs a fixed 1800ms loop tuned for the shimmer, while `SpriteAvatarWidget`'s controller (used everywhere else this accessory can appear) runs 900ms, so `_accFrame`'s cadence is deliberately doubled (`(_ctrl.value * 2) % 1.0`) to match rather than play at half speed. `den_share_screen.dart`'s copy stays on the accessory's static first frame instead, since it's a captured snapshot.

The Den's dynamic HUD elements (badges, trophy shelf, diamond, showcase, and the floor rug/dash texture) all check `hasImage` and skip their own flat-color placeholder once real art exists — a flat gray plaque or a dashed rug pattern reads as decor against the procedural painter but as a rendering glitch against a photo backdrop.

**`den_share_screen.dart`'s wall/floor colors fixed 2026-08-15 — real drift between the two hand-synced painters.** Its `_denPalette` was a hand-ported hardcoded switch covering 11 background ids — 9 of which (`bg_twinsuns`, `bg_stardust`, `bg_neoncity`, `bg_tallgrass`, `bg_dojo`, `bg_space`, `bg_yellow`, `bg_shelf`, `bg_podium`) don't exist in the current 52-entry catalog at all, leftovers from an earlier retired one. Every real current id fell through to one generic fallback color. Invisible for 48 of 52 backgrounds (`hasImage` skips painting these colors entirely once real photo art exists), but for the 4 procedural-only ids that actually need this (`bg_workbench`/`bg_snowfield`/`bg_maproom`/`bg_shadowrealm`), the shared Den image rendered visibly wrong colors compared to the live Den. Fixed by reading `bgArt.bgPalettes` directly, matching `den_scene.dart`'s own already-correct implementation — eliminates the drift risk going forward instead of just patching the stale values once more.

**Stale reference, not yet reconciled**: the two paragraphs above describe `SpriteAvatarWidget` directly, which predates the pixel-art cutover (see above) — the figure in the Den now actually renders through `AvatarWidget` → `PixelAvatarWidget`, and `_groundAccessoryOf()`'s lookup always returns `null` post-cutover (no `AccessoryPlacement` concept exists on `PixelCosmetic` yet), so the ground-accessory `Positioned`/`Image.asset` block in both files currently renders nothing regardless of what's equipped. The `avatarSize`/`groundRow` figure-placement math is unaffected (it positions the whole `AvatarWidget` box, not anything inside it) and should still be accurate.

### Collection data model (`lib/models/lego_set.dart`)

`LegoSet.num` is always stored **without** the trailing variant suffix (`-1`) — it's stripped on every write path via `num.replaceAll(RegExp(r'-\d+$'), '')` (see `CollectionProvider.addSet`/`importFromRebrickable`). API calls re-add it (`num.contains('-') ? num : '$num-1'` in `Api.fetchSet`). When adding a new code path that takes a set number from user input or an external API, normalize it the same way or lookups/dedup (`_sets.any((s) => s.num == num)`) will silently break. **`CollectionProvider.importJson()` (Settings > Restore from backup) missed this normalization until 2026-08-15** — it accepts arbitrary pasted JSON, not guaranteed to already be this app's own clean `exportJson()` output, so a `"75192-1"`-style `num` would silently fail the dedup check against an existing `"75192"` row and create a duplicate instead of updating it. Fixed with the same regex used everywhere else, applied before parsing.

`LegoSet.subtheme` is confirmed (2026-08-15) to be an **effectively dead field** for anything sourced from Rebrickable — `add_set.dart`'s `_save()` writes it from `_rb?['subtheme_name']`, a key Rebrickable's `/lego/sets/` response never actually contains (subthemes are modeled as parent/child theme hierarchy, already folded into the combined `theme_name` string `_resolveTheme` builds, e.g. "Star Wars > Ultimate Collector Series"). Every downstream consumer (achievements, bundles, hidden themes) already OR-checks `theme` alongside `subtheme` for exactly this kind of gap, so there's no functional breakage — just don't expect `subtheme` to ever actually hold data from this path.

Sealed and open condition are tracked as fully parallel data throughout: `ebaySealed`/`ebayOpen`, `phSealed`/`phOpen` price histories, `sealedZeroResults`/`openZeroResults`. `LegoSet.status` ('sealed'/'open') picks which side is "relevant," but `ebayAvg` falls back to the other condition if the relevant one has no data — `ebayAvgIsFallback` exists specifically so the UI can flag a displayed price as borrowed from the wrong condition instead of presenting it as a clean apples-to-apples comparison. `sealedZeroResults`/`openZeroResults` distinguish "searched, found nothing" from "never searched" — don't conflate a null price with a confirmed-empty search.

### Dashboard hierarchy (`lib/screens/dashboard.dart`)

Rebuilt from a flat stack of cards into three grouped sections — Today / Your Collection / Discover — after feedback that the old layout had no visual hierarchy telling you what mattered most. A new `_Hero` widget at the top consolidates what used to be two separate things (a header ROI badge and a lower Portfolio card) into one: wordmark, tagline, and the Market Value figure with its delta pill and sparkline together, so total collection value reads as the single headline number rather than being split across two places on the screen. `_TodayMiniCard` uses real `Icon` widgets instead of emoji specifically because emoji ignore Flutter's `color:` — they'd render in their own fixed color regardless of theme, breaking on any non-default theme. The stat row below the hero was trimmed from 4 cells to 3 (Sets/Sealed/Insider — Market was dropped as redundant once the hero already shows it prominently).

### External APIs (`lib/services/api.dart`)

Three different data sources, three different trust models:
- **Rebrickable** (set/theme lookup, collection import) is called directly from the app with an embedded key; theme names are resolved recursively (child → parent, e.g. "Star Wars > UCS") and cached in SQLite for 30 days (`Storage.getCachedTheme`/`cacheTheme`) to avoid re-walking the parent chain. `Api._resolveTheme` made public as `resolveTheme()` 2026-08-15 so `CollectionProvider.importFromRebrickable` (bulk "Import from Rebrickable") could call it too — **real bug fixed the same day**: bulk-imported sets never resolved `theme_id` at all, permanently leaving `theme: null` for every set imported that way. Nothing else in the app ever backfilled it after the fact (`fillImages`' own theme backfill only runs for sets missing an image, and bulk-imported sets already have one from the collection endpoint), so this was a real, silent gap — zero theme-based achievements/bundles/hidden-themes and no theme badge/dashboard grouping for anything imported this way, not just a cosmetic miss.
- **BrickSet** (retail price, barcode/EAN lookup) is also called directly (key is treated as low-sensitivity/public). See Barcode seeding below for the Worker-side `getSets` quota story — that quota is shared with these client-direct calls, which the Worker has no visibility into. **Instructions language picker fixed 2026-08-13** (`screens/set_detail.dart`): the language dropdown on a set's Instructions card, and its default-selected language, both followed whatever arbitrary order BrickSet's `getInstructions2` response happened to return entries in. Fixed to put English first when present, both in the dropdown list and as the default selection.
- **eBay** pricing goes through a Cloudflare Worker proxy (`K.workerUrl`) that holds the real RapidAPI key server-side and shares one cached result per set/condition across all users for 7 days (D1-backed). Client-side, `CollectionProvider.refreshEbay` additionally self-limits to 3 refreshes/week (tracked in the local `prefs` table via `Storage.recordQuotaCall`) — this is a separate, independent throttle from the server-side cache, not a reflection of it.

**eBay usage counter fixed 2026-08-15, was silently broken since it was built.** Settings' dev-gated "eBay API usage" tile (`handleEbayUsage`/`GET /ebay/usage`) always showed 0/1350 no matter how many real calls were made: the `ebay_usage` D1 table was referenced from the start but never actually created by any migration, so every read/write against it silently failed inside its own try/catch (`SQLITE_ERROR: no such table`) — the monthly cap could never actually trigger either. Fixed with a self-healing `CREATE TABLE IF NOT EXISTS` (`ensureEbayUsageTable`, called from both handlers). Even fixed, dev testing still wouldn't move the counter without a second change: the Worker's 7-day shared D1 price cache is checked *before* the usage increment, and "Force refresh all" only ever meant "ignore the client's own staleness check," never "bypass the Worker's cache too" — added a `force` flag on `POST /ebay` (bypasses the cache read only, the monthly cap check still applies) wired through `Api.fetchEbay`/`CollectionProvider.refreshEbay`, but scoped to `DevMode.instance.isOn && forceAll` only, so a regular user's "Force refresh all" behavior and cost profile are unchanged.

`FeatureFlagService` hits the same Worker's `/features` endpoint once at launch and fails safe to **all flags off** on any error (offline, timeout, non-200) — a flaky launch should never accidentally unlock a gated feature. Flags are toggled server-side (Cloudflare dashboard env vars, or `wrangler deploy --keep-vars --var NAME:value` from a terminal with wrangler access) with no app rebuild required. `FEATURE_COMMUNITY_FEED` and `FEATURE_SCANNER` are both **on** as of 2026-08-07 (real camera scanner and Community photo feed live for all beta users). `/features` also returns `community_banner` (free text from a `COMMUNITY_BANNER` env var, same toggle mechanism, empty/unset = no banner) — rendered as a persistent, non-dismissible notice at the top of `community_feed_screen.dart` via `FeatureFlagService.communityBanner`.

The Worker itself is Cloudflare-hosted, not a Flutter package — historically it lived entirely outside this repo, full file only ever handed over in chat and pasted in by hand (always give the user the complete `worker.js`, never a diff). **As of 2026-08-11 there's also `cloudflare-worker/` in this repo** (`wrangler.toml` + a working copy of `worker.js`, see that folder's own README) — no `wrangler.toml` had ever existed anywhere before that; it was reconstructed from the live worker's actual bindings/D1/R2/cron config via the Cloudflare API (`wrangler` here is authenticated with `workers:write`, confirmed via `wrangler deploy --dry-run`) since the dashboard-paste workflow left nothing to deploy *from*. The checked-in `worker.js` is the deployed bundle pulled via that same API, not the authored source — it's missing every doc comment (esbuild-bundled, no comments survived), though `handlePartsMerge` specifically has a real commented source now (`PARTS_MERGE_WORKER.js`, reconciled 2026-08-12 — see Parts Merger below) even though the rest of the file doesn't. Net effect: direct `wrangler deploy` from `cloudflare-worker/` is now possible and validated working (used for real 2026-08-12 to ship the Parts Merger BrickLink-id change below), but the hand-paste-to-dashboard workflow and "always give the complete file in chat" habit should continue for any other endpoint until the same reconciliation happens for it — don't hand-edit the bundle in `cloudflare-worker/worker.js` directly, it'll just get overwritten by the next real pull. Tightly coupled to app behavior worth knowing about: it also serves LEGO news/deals feeds, the Community photo moderation pipeline (Discord bot posts pending submissions with Approve/Reject buttons — must go through the real Discord Bot API, not a plain webhook, since webhooks silently drop the `components` field with no error), the crowdsourced barcode-consensus endpoint (`/barcode/submit`, see Anonymous device identity above), and Discord slash commands for posting news/deals (`/news`, `/deal`, `/deallink`, `/amazondeal`). `/amazondeal` specifically does zero scraping of Amazon's own pages (Amazon's Conditions of Use prohibit automated access) — it's manual-entry only, identical in shape to `/deal`, with the URL auto-tagged with the Associates tracking id (`AMAZON_TAG`) before insertion. If real Amazon pricing/title/image data is ever wanted, the compliant path is the Product Advertising API (requires 3 qualifying sales within 180 days to unlock for a new Associates account), not scraping — don't reintroduce a scrape-based version of this command.

**Automated deal candidate scanner** — same shape as the existing RSS news pipeline, not manual-entry like `/deal`/`/amazondeal`. `checkSlickdealsForDealCandidates(env)` polls Slickdeals' LEGO RSS feed (`SLICKDEALS_LEGO_RSS`), dedups against a `deal_seen` D1 table (mirrors how news candidates dedup), and posts up to 8 candidates per run to the mod Discord channel as `deal_post:<guid>` buttons. Clicking one opens a Discord modal (`DISCORD_MODAL = 9`) with `price` (required, prefilled via `extractPriceGuess()` — a regex over the title, not reliable enough to auto-post without a human glancing at it), `retail` (optional), and `url` (optional, "Direct retailer link for affiliate tag"). The `url` field exists specifically because Slickdeals' own `<link>` always resolves to `slickdeals.net/f/...`, never the real retailer — without it, `inferRetailer()`/affiliate tagging would silently have nothing to tag. `handleDealModalSubmit()` uses the modal's `url` if given, else falls back to the cached Slickdeals link, and its confirmation reply explicitly states whether an affiliate link was applied or not, rather than failing silently. This runs on its own cron schedule (`DEAL_CRON = '0 */6 * * *'`, every 6 hours, unchanged by the 2026-08-16 cron consolidation below since it was always correctly split out) — `scheduled()` branches on `event.cron` to route to the right job. No new slash command was needed for this; it rides the existing button/modal interaction handlers.

**Fixed 2026-08-14: Slickdeals candidates always posted with no picture.** `parseRssItems()` only ever looked for an `<img>` inside `<description>` — correct for the LEGO news RSS feeds (`RSS_FEED_SOURCES`), but Slickdeals' `<description>` is always plain CDATA text with no image at all; the real thumbnail only ever appears inside `<content:encoded>`, a tag this function never read. Fixed with a fallback to `content:encoded` when `description` has no `src=` match — kept `description` as the first choice so feeds that do put an inline `<img>` there keep working exactly as before.

### Barcode seeding (`runSeedBatch`/`discoverNewSets` in `cloudflare-worker/worker.js`) — real daily budget + hourly cron added 2026-08-16

`runSeedBatch` walks a `seed_queue` D1 table (fed by `discoverNewSets`, which pages through Rebrickable's `/lego/sets/` by `-year` and enqueues anything not already in `barcode_cache`) and, for each queued set, calls BrickSet's `getSets` once to pull its UPC/EAN and write both into `barcode_cache` (`ON CONFLICT` upsert — a set with both barcodes yields **two** rows per one successful call, so `barcode_cache` row growth is not the same number as `getSets` calls made; don't confuse the two when eyeballing progress). `runMonthlyCatchup` is a variant that re-walks from page 1 for the first `MONTHLY_CATCHUP_DAY_CUTOFF` days of each month to catch newly-added-to-Rebrickable sets that a purely forward-paging discovery would otherwise never revisit.

**The real constraint here is BrickSet's own `getSets` quota, not Cloudflare or this code.** BrickSet's docs describe a 100-calls/day default tier — but 2026-08-16 live testing against this app's *actual* production key (`env.BRICKSET_KEY`, confirmed genuinely set via `wrangler secret list`, not just the code's hardcoded fallback `BRICKSET_KEY_FALLBACK`) put 110 calls through in one day with zero errors, directly contradicting that generic number for this specific key (higher tier, or no hard synchronous enforcement — can't tell which from the outside; BrickSet's API exposes no rate-limit headers or remaining-quota field in either the response headers or body). `BRICKSET_SEED_DAILY_BUDGET` (currently `500`, deliberately generous rather than another guessed conservative number) is tracked against a real daily counter (`brickset_usage` D1 table, `day_key`-keyed since BrickSet's quota resets daily not monthly, same self-healing `CREATE TABLE IF NOT EXISTS` shape as `ebay_usage`) — `runSeedBatch` stops mid-batch the instant today's budget is spent rather than blindly attempting the rest of its pulled batch. `GET /brickset/usage` mirrors `/ebay/usage` for visibility. The real safety net going forward is watching `seed_errors` (already auto-logged on any non-200 BrickSet response) for the first actual sign of throttling — that's real evidence, worth trusting over another guess at the "right" number.

This budget only ever sees calls **this Worker itself makes** — it has zero visibility into the app's own client-direct BrickSet calls (`Api.fetchSetDetails`/`fetchSetExtras`/`fetchSetByBarcode`, all called straight from the Flutter app, bypassing the Worker entirely, see External APIs above), which share the exact same underlying `getSets` quota. That's a real, unclosed gap — if live app traffic and seeding both spike the same day, nothing here would catch it. Proxying those calls through the Worker (like eBay already is) would close it properly but hasn't been done.

**Cron schedule consolidated 2026-08-16, incidentally fixing a real mis-routing bug.** The Worker's `scheduled()` handler only ever special-cased `DEAL_CRON` — every *other* registered cron trigger fell into one shared branch that ran `runSeedBatch` + `cleanupExpiredCommunityPosts` + `checkRssForNewsCandidates` together, regardless of which specific time fired it. The original 4 crons (`0 15 * * *`, `0 3 * * *`, `0 4 * * *`, `0 */6 * * *`) had 3 separate daily entries that were consequently always redundant — `wrangler.toml`'s own old comment ("which one is which... determined by worker.js's own scheduled() handler branching") documented an assumption of per-time differentiation that the code never actually implemented. Discovered trying to just *add* a 5th cron (for more frequent seeding) and hitting a real, hard Cloudflare platform limit: **Workers Free allows only 5 cron triggers total per ACCOUNT, not per worker** — this account was already at that ceiling (the original 4 here + at least one on the separate `lego-rewards-watcher` Worker, see Push notifications below). Fixed by collapsing the 3 redundant daily entries into one hourly trigger — loses nothing (they were never differentiated to begin with) and incidentally closes the whole mis-routing question, since there's only one non-deal schedule left to route. `wrangler.toml`'s `crons` is now `["0 * * * *", "0 */6 * * *"]` — 2 slots, net −2 from the original 4, no Workers Paid upgrade needed. Net effect: seeding now runs automatically ~24x/day (was ~3x/day *by accident*, not by design) and is self-limiting against `BRICKSET_SEED_DAILY_BUDGET` regardless of how many times it fires.

### Parts Merger (`cloudflare-site/parts-merger.html`, `handlePartsMerge` in `cloudflare-worker/worker.js`/`PARTS_MERGE_WORKER.js`) — added 2026-08-11, MOC support + real export formats added 2026-08-12

Merges up to 20 official LEGO sets' piece lists into one combined shopping list (same part+color from different sets summed, not duplicated). The Worker only ever handles official set numbers — Rebrickable dropped MOC data from their public API in 2020, so a MOC id gets a specific rejection warning, not a generic 404. MOC support instead lives entirely client-side: the site's own copy explains that Rebrickable's *website* (not API) still lets you export a MOC's own parts list as CSV, and the page accepts uploading one or more of those. A small generic CSV reader (`extractPartsFromCsv`, header-alias matching so it tolerates Rebrickable's export headers, this page's own output, or reasonable variants) merges uploaded rows with the Worker's set-lookup rows through one shared code path — the Worker's own CSV response gets re-parsed through the identical reader rather than being treated as a special case.

Two downloadable outputs, not one — replaced a single CSV that vaguely claimed to be "importable into BrickLink's wanted list," which it never was:
- **PAB / Reference CSV** — the original plain output (`Part Number,Color ID,Color,Quantity,Spare Qty`), explicitly framed on-page as a manual checklist, not importable anywhere (LEGO's Pick-a-Brick store has no bulk-upload feature at all).
- **BrickLink Wanted List XML** — a real, verified-importable file (schema confirmed against BrickLink's own docs, `help.asp?helpID=2567`/`207`: `<INVENTORY><ITEM><ITEMTYPE>P</ITEMTYPE><ITEMID>/<COLOR>/<MINQTY>/<CONDITION>N</CONDITION></ITEM>...`, deliberately **no XML declaration** — BrickLink's uploader rejects one if present — and it's a real file-picker upload on BrickLink's side, not a paste box). Needs BrickLink's *own* part number and color ID, which are NOT the same as Rebrickable's internal ids — confirmed via a live API call that Rebrickable's parts response already carries these for free under `part.external_ids.BrickLink`/`color.external_ids.BrickLink.ext_ids` (no extra API cost, just previously-unread fields), and spot-checked as genuinely necessary: part `10201` on set 75192 resolves to BrickLink id `2436b`, not `10201` — a same-number assumption would have been silently wrong. Rows missing a BrickLink id (mostly MOC-CSV uploads, since Rebrickable's website export doesn't include one) are excluded from the XML rather than guessed at, with a warning explaining why and a pointer back to the CSV, which still has them.

`handlePartsMerge`'s CSV response gained two columns (`BrickLink Part Number`, `BrickLink Color ID`) for this — the only Worker-side change the whole feature needed, since the field was already in Rebrickable's response and just unused before. `PARTS_MERGE_WORKER.js` (the authored/commented reference doc for this one endpoint, per the "always give the complete file, never a diff" convention) had drifted badly from what was actually live before this — different response shape, no pagination, no MOC-rejection wording — reconciled into an accurate copy in the same pass.

Second of two website tools ported into the app as a real feature (Parts Merger's native port shipped 2026-08-13, see its own section below). ### Social share cards (`screens/set_share_screen.dart`, `screens/collection_share_screen.dart`, `modules/avatar/widgets/den_share_screen.dart`, `widgets/share/photo_backdrop.dart`) — added 2026-08-17

Three share surfaces, all following the RepaintBoundary → PNG → `share_plus` capture pattern `den_share_screen.dart` originated (see Backgrounds section above for its own history): a per-set card (share icon on `set_detail.dart`'s hero, top-right, mirroring the existing back button), a whole-collection summary card (`Settings > Tools > Share Your Collection`), and the pre-existing Den card. All three build on `LegoSet`'s/`CollectionProvider`'s already-existing `roi`/`portfolioRoi`/`topGainers` getters — no new pricing math needed, this is purely a presentation layer over data that already existed.

**Privacy default, a deliberate product decision, not an oversight**: cost paid and market value in real dollars are personal financial info a user might not want broadcasting publicly, so both the set and collection cards default to showing **ROI percentage only** (e.g. "▲ 42% ROI") with dollar figures hidden behind a "🔒 Value hidden" / "🔒" placeholder, plus a "Show \$ amounts" pill toggle to opt into revealing them before sharing. The collection card's top-gainers list is exempt from this toggle entirely — it only ever shows ROI% per set, never dollars, since there's no legitimate reason a leaderboard-style list needs real figures to make its point. **`widgets/share/photo_backdrop.dart`** is shared by all three screens: `pickBackdropPhoto()` reuses the exact camera/gallery bottom-sheet chooser `community_feed_screen.dart` already established (the native picker's own built-in camera button isn't reliable across Android skins, confirmed on a real device, hence asking explicitly), and `PhotoBackdropCard` composites a sticker over that photo on a 540×960 (9:16, Instagram/Snapchat Story shape) canvas — or, when no photo is picked, renders the card completely unchanged, so every screen's original plain-card look stays the default. Each of the three screens gained a small "Add a photo" / "Change photo" pill wired to this; Den's got folded into its existing A/B/C mode toggle rather than replacing it, since photo-backdrop and info-density (clean/stats/trophies) are orthogonal choices.

**Sticker redesign, 2026-08-17 — the first version reused the standalone card as the photo overlay, and it was wrong.** Initial ship just dropped each screen's full standalone card (built to be the entire share image on its own) straight onto the photo via `PhotoBackdropCard`. User feedback on-device: "the share pictures and cards look ugly together and overlap too much" — correct, since a dense multi-section card at full size swallows most of the photo it's supposed to be sitting on top of. Root cause was treating "add a photo" as a background swap on the *same* card rather than recognizing a photo overlay needs categorically less content and a hard size cap — a design gap, not a coding bug, and one a visual mockup before writing the widget would have caught (see the design-brainstorm Artifact from this same conversation for the comparison that led to the fix).

Fixed two ways: (1) `PhotoBackdropCard` now hard-caps whatever `card` it's given to `maxStickerHeight` (34% of the 960px canvas) via `ConstrainedBox`, and gained a `scrim` flag (default on) so screens whose sticker supplies its own contrast can skip the extra darkening gradient; (2) each screen now builds a **distinct, purpose-built sticker widget** for photo mode instead of reusing its standalone card — mapped by content fit after brainstorming against reference apps (Robinhood/Strava/Discogs-Untappd/Spotify Wrapped/PSA-StockX), user picked three:
- **Set → `_SlabSticker`** (`set_share_screen.dart`), PSA/StockX-style graded slab: a letter grade (`_grade()`, mapped off `roi` — A+/A/B+/B/C, `NR` if no ROI data) instead of a raw stat, the set's own real number as "CERT NO. {num}", ROI% as the headline figure. Opaque white card (`scrim: false`) — it supplies its own contrast, deliberately borrowing language LEGO investors already use for sealed/graded sets rather than adapting a generic finance-app look.
- **Collection → `_GlassSticker`** (`collection_share_screen.dart`), Strava-style frosted glass: `BackdropFilter` + `ImageFilter.blur` over a translucent white panel, Sets/Sealed/ROI in a 3-stat row. A real, deliberate material departure from BrikStax's hard-ink-border "brick" language used everywhere else — accepted specifically for this one card since a blurred panel reads as part of the photo rather than a card stuck on it. `scrim: false` since the blur supplies its own contrast.
- **Den → `_DenMinimalSticker`** (`den_share_screen.dart`), Robinhood-style minimal: no card background at all, just typography floating on the photo (trophy count as the headline number, since Den has no $/ROI to lead with) — the one sticker that genuinely needs `PhotoBackdropCard`'s default scrim, since it has no background of its own to supply contrast.

The `showDollars` toggle still applies to Set's slab and Collection's glass exactly as it did to the standalone cards (dollar figures swap into the same slot rather than adding height, keeping the size cap intact regardless of toggle state) — Den's sticker carries no financial data either way, same as its standalone card.

All three new/touched share call sites use the non-deprecated `SharePlus.instance.share(ShareParams(...))` (matching Parts Checker's export, not Den's/Settings' older `Share.shareXFiles` calls, which were left alone rather than churned just to match — see the note on that in Parts Checker's own section above).

### Android build toolchain overrides (`android/build.gradle.kts`)

This project runs a very new Android toolchain (Kotlin `2.3.20`, AGP `9.0.1`, Gradle `9.1.0` — see `android/settings.gradle.kts` / `gradle-wrapper.properties`). `sentry_flutter` 8.14.2's own bundled Android library module (not this project's code — its `android/build.gradle` inside the pub cache) pins itself to Kotlin `languageVersion = "1.6"` and `compileSdkVersion 34`, both of which are incompatible with that toolchain and fail the build with unhelpful generic errors (`:sentry_flutter:compileDebugKotlin` "Compilation error, see log for more details"; then `:sentry_flutter:checkDebugAarMetadata` "compiled against android-34" once the app transitively needs `compileSdk 36+` via `package_info_plus`). Upgrading `sentry_flutter` past 8.x to fix this at the source wasn't viable without a much bigger change — 9.x requires `web ^1.1.0`, which conflicted with `share_plus` 9.0.0's `web ^0.5.0` pin.

Instead, `android/build.gradle.kts` has two narrow, deliberately-scoped overrides:
- A project-wide `subprojects { tasks.withType<KotlinCompile>() { ... languageVersion.set(KOTLIN_2_0) ... } }` — safe to apply to every subproject since no other plugin in this project conflicts with a modern Kotlin language version, this one only exists to override `sentry_flutter`'s stale pin.
- A `project(":sentry_flutter") { afterEvaluate { ... compileSdk = 36 } }` — deliberately **not** applied blanket via `subprojects{}`/`plugins.withId("com.android.library")` the way the Kotlin override is. That was tried first and broke `:home_widget`, which reads `compileSdk` internally at a different point than `sentry_flutter` does and throws "too late to set compileSdk" once `afterEvaluate` has already fired for it — different plugins consume this value at different times, so a blanket override isn't safe here the way it is for the Kotlin compiler options. `afterEvaluate` itself is required (not just `plugins.withId`) because a plain immediate assignment runs *before* `sentry_flutter`'s own script sets its stale value, which then silently overwrites it right back — that failure mode looks identical to the fix not being applied at all, with no error to distinguish the two.

If `sentry_flutter` is ever upgraded to a version that no longer pins an old `languageVersion`/`compileSdk` itself, both overrides are likely safe to delete — but confirm the specific version actually fixed it (check its own bundled `android/build.gradle` in the pub cache) before removing either one, since the failure mode if removed prematurely is exactly this same set of unhelpful generic Gradle errors again.

**That upgrade happened 2026-08-07** — `share_plus` bumped to `^12.0.2` and `sentry_flutter` to `^9.25.0` together (done directly on the Mac, merged back into `main`). **Neither override above has been re-verified against the new sentry_flutter version yet** — per the paragraph above, check whether 9.25.0's own bundled `android/build.gradle` still pins a stale Kotlin `languageVersion`/`compileSdk` before assuming both overrides are still needed; they may now be dead weight safe to delete, or may still be required. This also unblocked a second thing riding the same `web`-package constraint: `firebase_core`/`firebase_messaging` (added the same week for push notifications, see below) had been deliberately pinned to old versions (`^2.32.0`/`^14.9.4`) specifically to avoid conflicting with share_plus 9.0.0's old `web` pin — once share_plus moved to 12.x (which itself needs `web ^1.0.0`), that old Firebase pin became the thing causing a *new* conflict instead, and had to be bumped back up to current (`firebase_core: ^3.8.0`, `firebase_messaging: ^15.1.5`) in the same pass. If a future dependency bump on either machine reintroduces a `web`-package conflict, check both share_plus *and* the Firebase packages — they're coupled through this shared transitive constraint, not independent.

**A third class of override was added later** (`flutter run` on-device, 2026-08-09) for a different failure: "Inconsistent JVM Target Compatibility Between Java and Kotlin Tasks." Newer Kotlin Gradle Plugin versions now hard-fail on this (previously just a warning); Flutter's own build output names six plugins in this project that apply KGP at all — `flutter_timezone`, `home_widget`, `mobile_scanner`, `package_info_plus`, `sentry_flutter`, `share_plus` — and each one's bundled `build.gradle` leaves its Java/Kotlin compile targets at whatever old, mismatched defaults it shipped with (confirmed different per plugin: `flutter_timezone` was stuck at Java 11, `home_widget` at Java 1.8). Since Gradle only reports the first failure per run, this surfaced as a whack-a-mole sequence — fix one plugin, rebuild, hit the next.

This needed **two separate fixes, not one**, because the Java and Kotlin sides behave differently under Gradle's evaluation ordering:
- The Kotlin side: folded into the existing blanket `subprojects { tasks.withType<KotlinCompile>() }` block (added `jvmTarget.set(JVM_17)` alongside the existing `languageVersion` override) — safe project-wide the same way that one already was; confirmed working immediately for both `flutter_timezone` and `home_widget` with no per-plugin scoping needed.
- The Java side: tried the same blanket way first (`subprojects { tasks.withType<JavaCompile>() { sourceCompatibility = ...; targetCompatibility = ... } }`) and **did not work** — `compileDebugJavaWithJavac` stayed at its stale value regardless, because AGP's own `android.compileOptions{}` DSL sets those properties on the task directly at its own later point, silently overwriting a plain `tasks.withType().configureEach{}` set earlier. Exact same ordering failure already documented above for `sentry_flutter`'s `compileSdk` override, just a different property. Fixed with the same scoped-`project()` + `afterEvaluate` shape, factored into a small `forceJava17()` extension function and applied per-plugin: confirmed necessary for `flutter_timezone` and `home_widget` (each hit as a real build failure in turn), and pre-applied to `mobile_scanner`/`package_info_plus`/`share_plus`/`sentry_flutter` too rather than waiting to hit each as its own separate failure, since they're the remaining plugins on the same list and the fix shape had already proven correct twice. `sentry_flutter` keeps its `compileOptions` inlined into its existing `compileSdk` block instead of calling `forceJava17()`, since it already had its own `afterEvaluate`/`LibraryExtension` scaffolding.

**The pre-applied `forceJava17()` sweep immediately surfaced a real, pre-existing bug of its own**, unrelated to `home_widget`/`mobile_scanner`/`package_info_plus`: `:share_plus:compileDebugKotlin` failed with cascading "Unresolved reference" errors on classes (`ShareSuccessManager`, `SharePlusPendingIntent`, etc.) that genuinely exist in `share_plus` 12.0.2's own Kotlin sources, in the same module. Root cause was the *original* blanket `languageVersion`/`apiVersion` override (from the very first `sentry_flutter` fix, months earlier in this session/history) — it had been applied project-wide across **all** subprojects on the reasoning "no other plugin conflicts with a modern Kotlin version," which was wrong: `jvmTarget` is a bytecode-output setting, safe to unify blanket, but `languageVersion`/`apiVersion` caps which Kotlin *language features* the compiler accepts at all — capping every plugin down to the same `2.0` ceiling that fixes `sentry_flutter`'s stale `1.6` pin also silently broke `share_plus`, which needs language features newer than 2.0 (available fine on this project's real compiler, 2.3.20, just rejected once artificially capped). Fixed by moving `languageVersion`/`apiVersion` out of the blanket `subprojects{}` block entirely and scoping it to only `project(":sentry_flutter")` (which also already holds its `compileSdk 36` + Java 17 `afterEvaluate` block) — every other plugin's Kotlin tasks are now free to compile at whatever version they actually need.

Net lesson, now proven twice over (once for `compileSdk`, once for `languageVersion`/`apiVersion`): for this toolchain, **`jvmTarget` alone is safe to override blanket across all subprojects** — everything else Kotlin/AGP-related (`languageVersion`, `apiVersion`, `compileSdk`, `compileOptions`) needs to be scoped to the one plugin that actually needs it, via `project(":x")` + (where AGP owns the property) `afterEvaluate`. Don't extend any future override blanket on the assumption "this one's probably fine everywhere" — that assumption has now been wrong twice.

**The re-verification flagged as pending above happened 2026-08-12.** Read `sentry_flutter` 9.26.0's own bundled `android/build.gradle` directly (pub cache) against the two `:sentry_flutter`-scoped overrides: it already declares `compileSdkVersion 36` itself, and sets no `languageVersion`/`apiVersion` pin at all — both overrides had been dead weight since the 9.25.0 upgrade, quietly doing nothing on every build with no signal they'd gone stale. It still hardcodes Java 8 (`compileOptions` + `kotlinOptions.jvmTarget`), the same stale-default problem every other plugin on the six-plugin list has, so `project(":sentry_flutter")` now just calls `forceJava17()` like the rest — the two dead overrides and the large comment blocks explaining them were deleted. **Not verified with an actual build** — Gradle builds can't run from the sandboxed environment used for this repo's day-to-day Claude Code work (see Commands above), so this is confirmed only by reading the resolved dependency's own build.gradle directly, not by a successful `flutter build apk`/`flutter run`. Worth an explicit rebuild-and-confirm next time either machine builds this project, same as the original overrides themselves were only ever confirmed by real build failures/successes.

Real Firebase Cloud Messaging, added 2026-08-07. Verified post-deploy that all 15 bindings (including every secret) and the `*/15 * * * *` cron survived.

### Community likes and Brik rewards (`community_service.dart`, `community_feed_screen.dart`) — added 2026-08-07

`CommunityPost` gained `likeCount`/`likedByMe`; tapping the heart calls `CommunityService.toggleLike`, which hits `POST /community/like` (toggle insert/delete against a `community_likes` D1 table, `UNIQUE(post_id, user_id)` enforced server-side — one like per device per post, same anti-abuse shape as barcode consensus voting). `GET /community/feed` now also takes an optional `user_id` query param so each post comes back knowing whether *this* device already liked it. ### Wishlist affiliate links (`services/affiliate_links.dart`, `screens/wishlist_screen.dart`) — added 2026-08-16

**Amazon has no compliant way to link a specific product.** There's no ASIN for an arbitrary LEGO set (Rebrickable doesn't provide one), and the only legitimate way to get one — Amazon's Product Advertising API — is the same one already gated behind "3 qualifying sales within 180 days" for a new Associates account (see External APIs above). Deliberately fails soft: `handleEbayProduct` returns `{found:false, reason:"not_configured"}` rather than an error when the secrets are missing (verified live), and `Api.fetchEbayProductUrl()` on the client returns `null` for any non-found case, so `wishlist_screen.dart`'s eBay chip transparently falls back to `ebaySearchUrl()` — this activates automatically the moment the two secrets are added via `wrangler secret put`, no app update or redeploy needed.

Now actively synced between this Windows machine and a Mac (for iOS builds, since `flutter build ios`/Xcode/CocoaPods only run on macOS) via normal `git push`/`git pull` — expect **real, substantive merge conflicts** going forward, not just noise, since both machines now do real work (e.g. the share_plus/sentry_flutter/Firebase saga above started as a genuine `pubspec.yaml` divergence between the two, not a trivial lockfile regen). When reconciling, don't assume either side's version should just overwrite the other's — ask what changed and why before discarding anything that looks deliberate. `key.properties`/`brikstax-release.jks` (Android signing) and any Firebase *service account* key are git-ignored and must never be committed; `google-services.json` (see push notifications above) is the one Firebase-related file that's fine to commit.
